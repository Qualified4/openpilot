# CCNC 차선 ROI 픽셀 감사와 GPU 비교 결과 — 2026-10-18

**판정: 현재 ROI를 이용한 추가 학습과 신규 모델 채택을 보류한다.** 원본 실선을 훼손하는 샘플링 결함을 재현했다. 원본 픽셀을 보존하는 대체 추출기를 추가했지만 목표 도색의 식별, 주변 도색 배제, 가림 판별까지 통과한 것은 아니다. 따라서 GPU 학습을 재개하지 않았다. 기존 활성 ONNX, 체크포인트, 검수 데이터와 원본 로그·영상은 보존한다. 신규 코드는 오프라인 감사용이며 CAN·계기판 디버그·조향·가감속·차선 변경·Xiaoge 경로에 연결하지 않았다.

## 1. 학습 중단과 보존

최신 중단 요청 시 제가 실행한 학습 작업은 모두 정상 종료한 상태였다. 알려진 세션의 정상 종료와 산출물을 확인했으며 다른 Python 프로세스는 중단하지 않았다. 시스템 전체 프로세스 명령행 조회는 Windows 접근 권한 때문에 수행하지 못했다. 남아 있는 Python 프로세스를 제 학습 작업으로 단정하지 않았다.

`.analysis/lane-model-comparison-20261018/ROI_REVIEW_HOLD.json`을 설치했고, `train_compare.py`는 입력 manifest의 상위 경로에 HOLD가 있으면 CUDA 초기화와 출력 생성 전에 실패한다. 기존 데이터의 HOLD도 유지했다. `QUARANTINE.json`은 이미 끝난 모든 실험의 채택 보류를 명시한다. 체크포인트·ONNX·학습 기록·임계값 74개 파일의 SHA-256을 `pixel-audit/trained-artifacts-before.json`에 보존했다. 초기 export 검증 실패 실험도 덮어쓰지 않았다.

기존 활성 모델 SHA-256은 `ea76f53a26cff8f0182700f39216475bd4b2454d5967dc48d991dd0b451b132f`이다. 새 모델을 여기에 복사하지 않았다. `CcncLaneTypeDetection` 기본 OFF와 기존 미리보기 전용 정책을 유지한다.

## 2. 투영·보정·동기화 감사

계산은 `p = K · view_from_device · R(rpyCalib) · [x,y,z]` 후 깊이로 나눈다. modelV2 좌표의 x는 전방, y는 우측, z는 아래 방향이며, lane z에 도로의 카메라 상대 높이가 이미 포함되어 있다. UI의 차선 투영도 z 보정 0을 사용한다. 카메라 높이를 다시 더하거나 좌우 축의 부호를 뒤집으면 안 된다.

242개 기존 관측을 canonical `get_view_frame_from_calib_frame(..., height=0)`와 별도로 비교했다. 중심 투영 최대 차이는 **0.00006081px**였다. 이는 구현 간 대수적 일치이며 실제 도색 정렬 오차가 이 값이라는 뜻은 아니다. generic intrinsics의 실물 오차, 보정 추정 오차, modelV2 경계 오차 및 렌즈 특성은 이 비교로 검증되지 않는다. model의 성긴 3D 점 사이에는 선형 보간을 사용한다.

새 미리보기의 train/validation 고화질 노란색 표본 4개를 원본 HEVC에서 다시 디코딩했다. `3ea/6`과 `3dd/5`는 각각 영상 1,200프레임, encode index 1,200개, index 0부터 연속이었다. 각 표본은 **encode segmentId → frameId·timestampEof → roadCameraState/modelV2**가 정확히 일치한다. 최근 시점의 다른 modelV2를 임의로 연결하지 않았다. B-frame은 없었다. 보정 정보의 나이는 130.5~237.1ms였으며 미래의 보정값을 사용하지 않았다.

장치는 MICI/OS04C10, 영상은 1344×760, K의 fx=fy=1141.5, cx=672, cy=380이었다. qcamera는 실제 영상 크기에 맞춰 K의 x/y 행을 각각 스케일한다. 이 방식은 기록 영상의 리사이즈에 대응하며 qcamera를 같은 종횡비로 가정하지 않는다. 이 감사의 원본 재디코딩은 고화질 두 세그먼트에 한정한다. 메타데이터 일치는 물리적 센서 시각까지 독립적으로 증명한 결과가 아니다.

상세 증거: `pixel-audit/exact-source/sync-audit.json`, `pixel-audit/results/pixel-audit.json`.

두 원본 rlog에서 비압축 `roadCameraState.image` 기록은0개였고 camera transform 필드는 비어 있었다. 따라서 숨겨진 영상 transform이 기록되었다고 가정해 보정하지 않았으며, 이 두 로그로 인코더 전후 압축 손실을 측정할 수 없다.

## 3. 확인한 변환 결함

| 경로 | 실제 처리 | 확인된 문제 |
|---|---|---|
| 기존 6~46m / 초기 dual ROI | 거리 등간격 192행, 64열, bilinear remap | 원거리에서 같은 원본 행을 반복 확대한다. 출력 행 간 간격이 실제 관측 해상도와 다르다. 짧게 자르는 것만으로 해결되지 않는다. |
| 최근 native v1 | 원본 정수 행 중 색상32/종류64행, 가로16점 선택 | 보간은 없지만 대부분의 픽셀을 생략한다. 도색 검출마다 행 중심을 이동시키고 미검출 행은 보정0으로 복귀한다. 주변 밝은 도색으로 중심이 옮겨갈 수 있다. |
| 신규 pixel ribbon | 원본 행의 연속된 모든 x 픽셀과 좌표를 가변 길이로 저장 | 포함한 픽셀의 보존은 검증했다. 목표 도색 선택과 신경망 입력으로서의 적합성은 미검증이다. |

native v1의 242관측/475 head에서 가용 원본 행 생략률은 평균 **48.60%**, p95 **78.13%**, 최대 **80.25%**였다. 이는 실제 분류 오류율이 아니라 정보 생략량이다. 폭 0.9m를 가로 16개 점으로 표현하면 선택 간격이 약 6cm가 된다. 행별 위치 추정·반올림·희소 선택의 조합은 계단과 지그재그를 만들 수 있으며, "보간하지 않는다"는 속성만으로 도색 보존을 보장하지 못한다. 검수 미리보기의 nearest 확대는 이 격자를 더 두드러지게 보이게 한다. 학습 입력 자체의 낮은 해상도와 검수 화면 확대를 구분해야 한다.

압축이 없는 합성 노란 실선에서 변환만의 문제를 격리했다.

| 실제 도색 폭 | 색상용 원본 도색 행 | v1 도색 완전 소실 행 | 종류용 원본 도색 행 | v1 도색 완전 소실 행 | 신규 ribbon의 도색 픽셀 소실 |
|---|---:|---:|---:|---:|---:|
| 3.5cm | 32 | 12 (37.5%) | 64 | 16 (25.0%) | 0 |
| 5cm | 32 | 0 | 64 | 0 | 0 |
| 10cm | 32 | 0 | 64 | 0 | 0 |
| 15cm | 32 | 0 | 64 | 0 | 0 |

3.5cm는 가는 도색/잔존 도색을 확인하는 스트레스 조건이며 일반 차선 폭의 실차 오류율로 제시하지 않는다. 소실된 행은 **원본에 도색이 있는데 변환 후 도색이 전혀 없는 행**이다. 실제 도로의 점선 공백이라는 의미가 아니다. 정상 폭 대조군의 완전 소실이 없었다는 사실도 함께 기록한다.

실제 `3dd/5 frame7039` 노란 실선의 부분 수동 trace에서는, 4.5~20m 중 기하적으로 가용한 행의 도색 3,051픽셀을 새 ribbon이 100% 포함했다. v1 종류 입력이 문자 그대로 유지한 원본 도색 픽셀은 4.65%였다. 이것은 픽셀 보존율 비교이며 정확도 95.35% 개선이라는 뜻이 아니다. 이 실사 표본에서는 v1 선택 행의 도색 완전 소실은 0행이었지만 중심/두께가 계단 형태로 나타났다. trace는 단일 assistant가 원본만 보고 작성했고 ±3px 오차를 둔다. 독립 검수 정답으로 과장하지 않는다.

기존 부분 trace 4개 중 4.5~20m 가용 행에 도색이 있는 3개의 ribbon 포함률은 100%, 100%, **81.04%**였다. 나머지 1개는 trace 전체가 해당 가용 거리/행 밖에 있어 측정 불가다. **81.04% 사례가 남아 있으므로 목표 도색 정렬을 해결했다고 판정하지 않는다.** 이중선 일부, model 경계 불일치, 횡단 도색 혼입을 별도 검수해야 한다.

원본 재디코딩 RGB를 lossless PNG로 저장하고 재읽어 byte equality를 확인했다. 이후 대응 좌표의 RGB 차이도 246관측에서 0이다. 이 결과는 "포함된 decoded source 픽셀을 새 추출기가 바꾸지 않았다"는 뜻이다. 센서 RAW와 HEVC 전 영상이 없어 압축 자체의 손실량은 **측정 불가**다. 원본부터 흐린 부분을 변환 오류라고 단정하지 않았고, 합성 재현으로 새로 생긴 오류만 구분했다.

## 4. 새 추출기의 범위와 남은 조건

`pixel_ribbon.py`는 4.5~20m를 기본으로 원본 행에 투영되는 좌우 경계를 구하고, 내부의 모든 정수 픽셀을 `rgb, xy, distance_m, row_offsets`로 반환한다. 원본 색상/좌표를 유지하고 행별 밝은 점 재중심화, remap, resize, 검은 패딩을 하지 않는다. 가림/화면 밖 구간은 빈 행으로 명시하며 서로 이어 붙여 도색 공백을 만들지 않는다. 실제 시작점은 첫 기하적 가용 행으로 이동한다. 가림과 보닛 제외는 현재 보수적 추정이므로 실제 도색 가용성을 확정하지 않는다.

색상은 이 관측 중 가까운 12m 이내를 우선 사용하도록 설계하고, 종류는 20m까지 사용한다. 필요 시 별도 호출의 상한은 25m이며 무조건 확장하지 않는다. 출력 거리값은 model 경계의 전방 거리 및 행 깊이의 근사값이다. 곡선 차선의 누적 호장이나 모든 픽셀의 독립적인 3D 깊이를 측정한 값은 아니다.

원본 사각 crop도 크기 변경 없이 보존하되 별도의 ribbon mask를 제공한다. mask 바깥을 검게 칠한 이미지를 학습에 넘기지 않는다. 전체 ribbon에는 주변 표지가 포함될 수 있으므로 **도색 있음/공백 및 최종 클래스는 기본 UNKNOWN**이다. 밝기 마스크를 ground truth로 복사하지 않는다. 가림 없는 도로라는 독립적인 근거 없이 도색 미검출을 공백으로 바꾸지 않는다.

이 가변 길이 표현은 기존 PP-LCNet의 고정 입력과 호환되지 않는다. 새 추출기와 기존 모델을 즉시 연결하지 않았다. 다음 학습 전에 원본 crop+위치 mask 또는 검증된 원본 특징 집합 중 입력 계약을 확정하고, 실제 목표 도색의 위치·방향·폭이 보존되는지 검수해야 한다. 횡단보도와 연결된 도색, 유도선, 이중선, 그림자, 선행차 경계가 아직 주된 잔여 실패 조건이다.

## 5. 시간적 판별 설계와 기존 시제품의 한계

오프라인 `temporal.py`는 최근 3초, 0.25m bin, 속도 적분을 사용한다. 한 프레임의 여러 행과 겹치는 프레임은 같은 bin에 중복 가산하지 않는다. 모순은 다수결 대신 UNKNOWN으로 만들고, 차선 변경·시간 단절·경계 점프·추적 상실 시 초기화한다. 도색 3회/내부 공백 2회 및 충분한 고유 관측 거리가 있어야 점선 후보가 된다. 짧게 보이는 실선 조각만으로 실선을 확정하지 않는다. 기존 최대0.5초 표시 유지와 독립 head 상태는 그대로 둔다.

하지만 현재 시제품의 `이동거리 + 전방거리`는 직선 근사다. 곡선·회전·경계 추적 오차에서 동일한 실제 도색이라는 보장은 검증되지 않았다. 신규 lossless 관측은 아직 paint/gap UNKNOWN이므로 이 시제품에 확정 증거로 공급하지 않는다.

다음 구현은 타임스탬프가 일치하는 ego pose/회전과 추적된 경계의 호장을 이용해 원본 도색 관측을 같은 경계 좌표에 투영해야 한다. 위치 불확실성이 bin 폭을 넘거나 추적 대응이 불안정하면 합치지 않는다. 정차는 같은 공간의 재관측으로 처리하며 길이를 늘리지 않는다. 가림은 gap이 아니라 미관측이고, 차선 변경은 양측 상태를 초기화한다. 색상에는 가까운 실제 목표 도색 픽셀만 사용하며 횡단 표지와 주변 노란 시설물을 분리해야 한다. 이 조건들을 실제 로그의 수동 대응점으로 검증한 후 확정률과 지연을 평가해야 한다.

## 6. 데이터 확대 및 이미 종료한 GPU 실험

아래 수치는 모두 **문제 ROI를 사용한 보존 실험의 진단 결과**다. 신규 ribbon으로 얻은 정확도나 채택 검증 결과가 아니다.

보유 파일 405개를 조사한 inventory를 재사용했다. 중복을 합치면 27 route, 189 log 세그먼트, qcamera168/고화질24 세그먼트이며 같은 세그먼트에 양쪽 영상이 있는 것은 6개다. 기존 전체 후보 112,342개라는 보고와 이번 세부 처리의 모수는 다르다. 기존 관측 충분·차선변경 제외 22,251개를 모두 다시 처리했고, 별도 원본 픽셀 수집은 기존 정확 동기화/기하 유효 후보 **88,466개**를 대상으로 했다. 후자는 5Hz 후보이며 모든20Hz 프레임을 학습했다는 뜻이 아니다.

22,251개 재검토에서 시간 일관성 기반 자동 제안 1,532개를 얻었지만 근접 중복 1,330개 등을 제한했다. 검수 후보 확장에는 모호한 장면도 포함했고 원본 context와 두 head를 나란히 검수했다. 총609개 검수 항목은 단일 assistant 시각 검토이며 사람의 독립 승인으로 취급하지 않는다. 라벨 제안/개별 승인/보류와 기존 라벨 충돌을 별도 JSON에 보존했다. 88,466개 중 양쪽 head가 생긴 것은40,649개, 한쪽 이하47,817개였다. 자동 제안이 많아도 검증되지 않은 채 학습에 투입하지 않았다.

자동 규칙의 train-only 층화 감사 결과는 다음과 같다. 기존 검수 정답을 자동 규칙 튜닝용 테스트로 사용하지 않았다. 독립성을 보장할 수 없는 인접 장면은 route/segment/10초 그룹으로 묶어 보수적인 상한도 기록했다.

기존 자료 대조군은 train50개/11route, 확장 실험은 train170개/12route였다. validation44개/4route와 test173개/7route는 동일하다. route 분할은 기존 잠금을 유지했다. train170은 흰 점선101/흰 실선42/노란 실선27, validation은30/3/11, test는114/38/21이다. 노란 점선은 없다. test173은 동일 장면의 대체 화질을 합쳐152scene이며 fcamera76/qcamera97이다. 화질 쌍은 같은 분할에 있고 다른 시간 프레임의 라벨을 임의로 공유하지 않았다.

초기 native validation의 노란색 표본이 모두 화질/관측 gate에서 제외되는 문제가 있어 validation route의 노란색11개를 추가 검수했다. 일부 관측 문턱이 완화된 별도 검수 표본이므로 완전 자동으로 일관되게 입학한 데이터라는 주장도 하지 않는다. 현재 픽셀 감사 결과 때문에 이 데이터와 결과 전체를 다시 보류했다.

GPU는 기존 `.analysis/gpu-training-20261018/venv`의 torch2.6.0+cu124/CUDA12.4/RTX4090을 사용했다. torchvision0.21.0+cu124만 별도 GPU 환경에 추가했고 기존 CPU torch2.6.0+cpu 환경은 유지했다. 네 모델의 공식 ImageNet pretrained 가중치를 사용했으며 출처·SHA는 `pretrained/sources.json`에 있다. model/input/target/loss weight/역전파 gradient의 cuda:0와 유한 gradient를 기록하고, 저장된 body 가중치가 pretrained에서 실제로 변경됐는지16실험 모두 확인했다.

전체 클래스별 Precision/Recall/F1, macroF1, fcamera/qcamera와 환경별 표는 `comparison-tables.md`, 원시 값은 `comparison.json`에 있다. 기존자료 대비 확장자료 종류 정확도 변화는 PP.25 −5.20pp, PP.5 −5.20pp, Mobile −6.94pp, Shuffle +4.62pp였다. 전체 모델이 개선됐다고 결론내릴 수 없다. 40epoch끼리는 update80→240 차이가 있고 동일-update 탐색 대조군도 보존했다. f-only/q-only 통제 실험은 없어 혼합 학습 자체의 인과적 개선율은 **측정 불가**다.

validation 원시 macroF1 평균으로는 PP.5가 선택됐지만 표본이 작고 ROI가 미검증이므로 채택하지 않는다. Shuffle의 일부 test 수치가 높다는 이유로 모델을 다시 선택하지 않는다. 학습/검증 손실은 모델별 JSON과 `training-loss.png`에 보존했다. 마지막 epoch 대신 validation 최소 checkpoint를 사용했고 후반 validation 손실 상승도 숨기지 않았다.

173개에서 원시 False Dashed는 각각14/59,20/59,18/59,9/59이며 노란→흰 오류는11/21,7/21,8/21,7/21이었다. 최종 표시 확정률은8.67%,8.67%,19.65%,15.61%로 낮다. PP.25/PP.5의 최종 False Dashed는 각각1/13,1/10이며 Mobile/Shuffle은 각각0/14,0/12였다. 이 작은 분모로 희귀 오류 안전성을 인증할 수 없다.

같은 두 구간의 dense 검수142개에서는 단일 프레임 최종 확정률19.72~42.25%에 비해 시간누적 확정률0~5.63%였다. 시간누적의 점선 확정은 모두0개여서 False Dashed 비율은 **측정 불가(분모0)**다. 나머지 모델은 노란색 주황표시8개만 확정했다. 대부분을 숨기는 결과를 개선으로 주장하지 않는다. 표시 변경은 시간누적0~1회였으나 확정된 흰색 종류의 인접 쌍이0이므로 점선↔실선 전환율도 측정 불가다. 실제 도색 변경 시작 시각을 라벨링하지 않아 점선 확정 지연은 측정 불가이며 clip 시작 지연과 혼동하지 않는다.

환경별 test는 야간8개, 곡선27개, 저속1개, 정차1개, 차선변경0개다. 저속·정차·가림의 잘못된 실선 확정, 오전환, 미확정률을 신뢰성 있게 비교할 충분한 독립 장면이 없다. 신규 ribbon 정확도·노란 Recall·False Dashed·확정률·판정 지연은 **학습 미재개로 측정 불가**다.

기존 활성6~46m 모델/OpenCV와 정확히 같은 정답 장면이 겹치는65개만 비교한 결과도 보존했다. 기존 모델 종류87.69%/색상81.54%, 기존 OpenCV12.31%/24.62%였다. 시스템 입력과 학습 조건이 다른 native 모델을 비교한 수치는 `matched-active-comparison.json`에 있으며 ROI 변경만의 개선율로 해석할 수 없다. 해당 OpenCV 정확도로 성능이 충분하다고 추천하지 않는다.

## 7. PC 비용과 comma 검증

PC 추론은 Windows/OpenCV DNN CPU 1thread, 양측2개 batch,160회/32초/약5Hz다. 전처리·원본 RGB 특징·IPC·디코딩·표시를 제외한 신경망 시간이다. RSS 표본 최댓값은 PP.25 54.33MiB, PP.5 59.20MiB, Mobile72.48MiB, Shuffle57.85MiB였다. 모델별 CPU는 한 코어 기준 약0.73~1.90%였지만 Windows CPU 시간 counter가 거칠어 모델 간 순위를 단정하지 않는다.

오히려 기존 native v1 양측 고화질 RGB 특징 추출은 평균34.748/p95 44.643/p99 47.324ms, 한 코어 CPU18.07%, RSS54.31MiB였다. 시간누적 갱신은0.381/0.550/0.617ms였다. 이 수치는 같은 입력을 반복한 비용 벤치마크이며 실제 이동의 정확도 검증이 아니다. 새 pixel ribbon의 실시간 NV12 구현 및 비용은 측정하지 않았다. 신경망만 빠르다고 전체 파이프라인이 가볍다고 판정하지 않는다.

comma는 연결되어 있지 않다. **Snapdragon CPU/RSS, ON/OFF 추가 부하, modeld/controlsd 주기·지연, 프레임 누락, 실차 NV12와 기록 HEVC의 정확도 차이는 모두 측정 불가**다. 사용자 제공 Xiaoge 기준 평균738ms/CPU약160%/RSS약216MiB는 참고값이며 다른 입력·장치·측정범위의 PC 결과와 비교해 추가 부하 감소율을 계산하지 않았다.

## 8. 재개 조건과 적용 판단

우선 채택할 표현은 늘린 사각 strip보다 **원본 좌표를 보존하는 관측**이다. 다만 이번 ribbon은 픽셀 보존만 통과했으며 도색 의미/정렬은 통과하지 못했다. 재개 전에 다음 증거가 필요하다.

1. train/validation에서 독립 검수한 목표 도색 mask와 제외 대상(횡단보도/유도선/가림/시설물), 원본-입력 대응. 거리별 실제 도색 포함률과 false gap을 동일 가용 행에서 평가한다.
2. 원본 해상도에 맞는 두 head 입력 계약. 반복 확대/희소 샘플의 손실을 재도입하지 않으며 새 구조에도 보존 검사를 적용한다.
3. 직선·곡선·저속·정차에서 물리적으로 같은 도색의 추적 대응과 중복 제거 검증. 경계 변경/가림/추적 실패에서 UNKNOWN 및0.5초 만료를 검증한다.
4. 새 관측 규칙·입력·라벨 조건을 잠근 뒤 GPU 비교를 재개한다. 기존 test는 이미 열람했으므로 조정에 사용하지 않고, 추가 미열람 평가 장면을 별도로 남겨 검증한다.
5. 모델 선택 후 실제 comma에서 동일 입력 ON/OFF replay와 NV12 정확도를 측정한다. 그 이후에도 Sonata 숨김/점선 코드의 별도 계기판 검증 전 CAN 연결은 하지 않는다.

현재 네 모델과 OpenCV 모두 채택 보류다. 기본 OFF, 실제 CAN 미연결을 유지한다. DBC 표시 후보1/2/4/8과 미문서화10/14의 실차 지원은 이번 영상 감사로 검증되지 않는다. 기존 이탈/사각지대 경고 및 CCNC 디버그 우선순위에 대한 코드는 수정하지 않았다.

최종 검증은 기능·표시·시간누적·픽셀 보존·학습 차단 테스트 **57개 통과**, 이번 작성/변경 코드의 Ruff 검사 통과다. 보호 스냅샷13,164개 중 차이는 학습 도구 `model.py`/README와 동시 진행된 별도 CCNC 디버그2파일뿐이었다. 별도 디버그 파일은 이 작업에서 편집하거나 되돌리지 않았다. 원본 로그·영상405개와 이미 생성된 학습 산출물74개의 SHA는 모두 일치하고 활성 ONNX도 동일하다. native build, 실제 comma replay와 계기판 검증은 수행하지 않았다.
