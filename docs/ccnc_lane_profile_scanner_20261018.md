# CCNC 차선 1차원 경계 프로파일 스캐너 — 오프라인 프로토타입 검증 (2026-10-18)

기존 Pixel Ribbon·Hybrid Tracker와 분리된 `tools/lane_profile/`에 구현했다. 기존 ONNX(SHA-256 `ea76f53a…b132f` 유지)·데이터·CAN·CCNC 디버그·주행 제어·`lane_type` 코드는 변경하지 않았고, GPU 재학습과 런타임 교체는 하지 않았다.

## 구조
- 현재 modelV2 경계를 따라 4.5~20m의 **원본 정수 행 하나당 출력 행 하나**(세로 보간 없음), 가로 ±0.75m 미터 단위 96열 strip을 Y/UV 평면에서 직접 뽑는다.
- 행마다 도색/노면/UNKNOWN을 판정한다. 가림(lead 박스), 그림자 띠·급격한 조도 변화, 노면 홈 무늬, 이 선의 도색보다 훨씬 약한(마모) 도색, 횡단 도색, 경로 없음은 모두 UNKNOWN이며 공백이 아니다. 노면은 같은 프레임의 강한 도색에서 8m 이내이고 그 도색 대비의 25% 미만일 때만 인정한다.
- `s = 주행거리 + 행 거리`의 0.25m bin에 누적한다(±1m 1차원 상관 보정). SE(2)/3D 자세·Optical Flow·영상 정합은 쓰지 않는다.
- **점선:** 길이 1.5m 이상인 두 도색 그룹 사이에 1m 이상의 확정 노면이 있어야 한다. 노면 bin은 1m 이상 이동한 뒤 서로 다른 시점에서 2회 이상 확인되어야 한다(정차 중에는 점선을 새로 확정하지 않는다).
- **실선:** 마지막 공백 이후의 연속 도색이 12m 이상이면 실선이다. 12m는 학습 route에서 실측한 점선 3,469개 분포에서 정했다. 중앙값 4.0m, 95번째 백분위 10.25m이고, 10~11m 211개 다음 11~12m 21개로 급감하며, 98.4%가 12m 이하다. 실선 진입 뒤 남은 옛 공백으로 점선이 유지되지 않게 했다.
- **색상:** 12m 이내 도색의 도로 대비 색차 `dCr−dCb`가 4.5 이상이면 노란색, 2 이하면 흰색이고, 그 사이는 UNKNOWN이다. 기준은 학습 route 검수 프레임에서 정했다.

## 경량 strip 모델 학습 (RTX 4090, 추가)

입력은 4.5~20m 행 정렬 strip(YCbCr 128×96)만 사용했다. 데이터는 `.analysis/lane-dataset-20261018/`(train 8,900 / validation 1,750, 출처별 가중치)이고, 기존 활성 ONNX는 라벨 생성에 쓰지 않고 비교에만 썼다. 노란 점선은 학습 클래스가 아니며, 모델이 점선+노란색을 내면 UNKNOWN으로 처리한다. `train_strip.py`로 2개 구조 × 3개 시드 × 40 epoch를 학습했고, GPU 시간은 약 2분이다. 모델 선택과 확정 임계값(0.99)은 validation route로만 정했다. 사람 확정 test 세트(구간 10개, 424프레임)는 학습 후 한 번만 평가했다(`evaluation.json`). 평가 전 모델 해시는 `FROZEN-before-test.sha256`에 고정했다.

- 선택 모델: StripNet(깊이별 분리 CNN). 파라미터 21,532개, ONNX 93KB(기존 245,308개, 1.0MB). PyTorch와 ONNX 출력 차이 3.6e-7.

- Snapdragon에서는 측정하지 않았다.

해석:
- validation 라벨 대부분은 스캐너가 만든 것이라, 스캐너와의 비교는 스캐너에 유리하다(순환).
- test에서 False Dashed 20건은 스캐너의 알려진 출구 분기 오류 구간 하나에서 나왔다. 모델은 임계값 적용 시 이 구간을 UNKNOWN으로 남겼다.
- 노란색은 test의 단일 노란 구간(28프레임)에서 모델과 스캐너 모두 약했다.
- test 세트는 검수 과정에서 고른 10개 구간이고 프레임끼리 상관이 있어, 일반화 성능을 인증하기에는 작다.
- 런타임 전환과 CAN 변경은 하지 않았다.

## 실차 통합: CCNC 계기판 차선 종류·색상 표시 (2026-10-19)

- 테스트: CCNC 표시 27개(우선순위 전 조합, 좌우 독립, 만료, OFF·만료·무결과 시 ADRV_0x161 전체 값 동일, BSD·숨김 우선), 런타임 8개(2회 확인·0.5초 만료·차선 변경 초기화, 수신 시각 기준 만료, 모드별 인식기만 생성, OFF 무import, NV12 stride, 가짜 IPC로 데몬 전체 루프·모드 전환·OFF 종료), 표시 정책/기존 lane_type 회귀 포함 101개 통과. opendbc·CCNC·위키 묶음 2,867 통과, 57 실패는 HEAD `hyundaicanfd.py`에서도 같은 57개(EV 모드·레이더·scalar·조향 모드, 이번 변경과 무관).

## 카메라 프레임–modelV2 동기화 개선 (2026-10-19)

이전에는 conflate된 최신 1프레임과 modelV2의 frameId·EOF가 완전히 같을 때만 처리했다. 이제 `marking_daemon.FrameBuffer`가 모든 도로 카메라 프레임을 받아 최신 3개만 보관한다. 각 프레임의 frameId·EOF는 recv 시점에 함께 저장하고, 더 오래된 프레임은 버린다. 버퍼는 camerad 공유 메모리 참조이며 픽셀을 복사하지 않는다. camerad는 18개 버퍼를 약 0.9초 주기로 재사용한다.
- 선택 순서는 modelV2가 쓴 프레임(같은 frameId·EOF)이 먼저다. 없으면 modelV2 `timestampEof`(입력 프레임 시각, 수신 시각이 아님)와 EOF 차이가 50 ms 이하인 최근접 프레임을 쓴다.
- 이웃 프레임을 쓸 때는 처리 시각을 그 프레임 EOF로 하고, 차선·선행차 x를 vEgo×시차만큼 당긴다(직진 근사).
- Scanner/StripNet, 0.90, 표시 필터, CCNC 우선순위, card/CAN 경로는 그대로다.

기존 로그 190 세그먼트(modelV2 223,603개)의 실제 발행 시각으로 시뮬레이션했다(`tools/lane_profile/sync_analysis.py`).
- modelV2는 자기 프레임 발행 37~53 ms 뒤(p5~p99)에 도착한다.
- 카메라 EOF 간격은 p1 40.2 ms, 중앙값 50.0 ms, p99 59.7 ms다. 한 프레임 간격의 50.2%만 50 ms 이하이고, 두 프레임 간격은 최소 77.8 ms다.

### 버퍼 재사용 보호 (2026-10-19)

camerad의 ISP는 프레임 r의 슬롯을 r+18 프레임을 읽어 들이는 동안 덮어쓴다. 이 시점은 camerad가 슬롯의 frame id를 새로 기록하기 전이다. 따라서 수신 후 보관 시간이 기본 보장이고, `buffer.frame_id`는 보조 확인으로만 쓴다. 근거는 `.analysis/lane-marking-vipc-buffer-20261019/`에 있다.
- 선택된 프레임을 두 번 확인한다. 한 번은 픽셀을 읽기 전, 한 번은 strip 추출과 인식이 끝난 뒤다. 보관 시간은 `recv` 시각부터 잰다.
- 보관 시간이 0.5초 이상이거나 슬롯의 frame id가 저장한 frameId와 다르면 그 프레임은 버리고 결과를 발행하지 않는다.
- 픽셀을 읽은 뒤에 버린 경우에는 오염된 샘플이 남지 않도록 Scanner 추적 상태도 초기화한다. StripNet은 프레임마다 상태가 없다.
- 드롭 카운터는 `drop_hold_before`, `drop_frame_id_before`, `drop_hold_after`, `drop_frame_id_after` 네 가지이고, 다음 발행 패킷의 `counters`에 실린다.
- 3프레임 매칭, 50 ms 허용, 이동거리 보정, Scanner/StripNet, 0.90, 표시 필터, CCNC 경로는 그대로다.
- 실제 msgq VisionIPC(WSL 공유 메모리, Python 서버, 18버퍼)에서 실제 `marking_daemon.main()`을 Scanner와 StripNet으로 각각 돌려 확인했다.
  - 정상 프레임과 0.3초 보관 프레임은 발행했다.
  - 0.6초 정지(추출 전), 0.6초 처리(추출 후), 슬롯 재발행은 각각 해당 카운터로 버렸다.
