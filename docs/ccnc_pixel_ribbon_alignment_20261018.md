# Pixel Ribbon v2 흰 점선·실사 공간 정렬 후속 검증 — 2026-10-18

판정: **흰 도색 픽셀 누락은 개선됐지만 두 문제가 모두 해결된 상태는 아니다. 실사 흰 점선 확정과 전 구간 물리 정렬은 보류한다. GPU 재학습·모델 승격을 재개하지 않는다.**

기존 도색 선택 개선, 원본 픽셀 입력, 4.5~20m 관측, 최근 3초 거리 누적을 유지했다. 도색 선택·오프라인 검증 코드만 변경했다. CAN, CCNC 디버그, 주행 제어, Xiaoge, 활성 ONNX, 옵션 기본 OFF는 변경하지 않았다. 이 보고서의 종류 출력은 미검증 오프라인 진단값이며 실차 표시 확정이나 학습 정답으로 승인된 값이 아니다.

## 비교 자료와 보존

- 기존 3개 route·4개 segment·5개 클립의 HD 원본 80프레임을 그대로 사용했다. 두 흰 점선 클립은 32프레임이다. 새로운 무작위 주행 구간을 추가하지 않았다.
- 같은 80프레임 바로 다음 영상 프레임 80개를 추가 디코딩했다. `roadEncodeIdx.segmentId`로 영상 인덱스를 대응하고 frameId와 timestampEof가 modelV2·roadCameraState와 정확히 일치하는 경우만 사용했다. 임의의 인접 modelV2로 대체하지 않았다. 인접 관측은 약 50ms 간격이며 기존 분류 비교 80프레임 수에는 포함하지 않았다.
- 기존 train/validation route 구분을 유지했다. 테스트 route는 사용하지 않았다. 현재 검증은 반복 개발 검증이며 독립적인 blind test가 아니다.
- 기존 부분 검수 polygon·허용 오차를 변경하지 않은 비교를 기본값으로 삼았다. 신규 끝점 검토는 별도 파일이다. 초기 그리드 눈대중 끝점 좌표는 부정확해 폐기했으며 원본 파일과 잘못된 결과도 `*-initial-rejected.json`으로 보존했다. 최종 두 끝점은 원본 밝기 성분의 말단에서 좌표를 추출했다. 독립적인 사람 검수 승인은 없다.
- 이전 전체 결과는 `.analysis/pixel-ribbon-tracking-20261018/`에 보존했다. 이번 결과는 `.analysis/pixel-ribbon-alignment-20261018/`이다. 중간 후보도 `development-first/`, `development-before-attitude/`, `probe-*`로 구분했다.

## 흰 점선 누락의 원인과 수정

`18379`의 기존 부분 trace에 겹치는 관측 가능 42개 행 중 27개만 도색으로 선택됐다. 누락 부분은 원본에 파란 색조의 그림자 속 흰 도색이 실제로 남아 있었다. 대표 누락 행의 HSV 채도 중앙값은 약 94~119로 기존 흰색 `S≤75` 조건을 초과했다. 도로 대비 밝기는 상당수 행에서 26~40 수준이었다. 모델 중심의 대규모 이탈보다 **색상 후보 탈락과 그에 따른 폭 축소**가 주원인이었다. 끝의 희미한 한 행은 여전히 UNKNOWN이다. 마모와 압축·그림자 효과를 모두 개별 정답으로 구분할 근거는 부족하다.

차가운 그림자 색조를 흰색 후보로 허용하되 기존 거리·폭·방향·모델 주변 탐색·이전 경계 대응 조건은 유지했다. 노란색은 배타적으로 처리한다. 흰색 각 밝기 run에는 원본 밝기 대비 30 이상의 중심 증거를 요구해 아스팔트 무늬만 도색이 되는 경우를 막는다. 밝은 run의 가장자리는 기존 대비 18 기준으로 보존한다. 이 색상·밝기 규칙은 train 장면과 합성 대조로 만든 휴리스틱이며 신뢰도 확률로 보정된 수치가 아니다.

흰색 후보 확장 때문에 노란 이중선과 어두운 주변이 넓은 도색으로 합쳐지는 회귀를 발견했다. 혼합 도색 폭 판정에서 차가운 그림자 후보를 노란색에 합치지 않도록 수정했다. 차가운 후보 자체의 폭 제한은 유지한다. `8355`의 포함률은 기존 값으로 복구했다.

`38875`는 원래 밝은 흰색 도색 대부분을 선택했다. 개선 후에도 두 행은 폭·주변 밝은 성분의 분리 근거가 부족하다. 그 행을 강제로 채우거나 공백으로 만들지 않았다. 원본에서 실제로 도색이 없는 부분과 검출 실패는 모두 자동으로 같은 음성 정답이 되지 않는다.

## 흰 점선 시간 누적의 별도 실패 원인

합성 흰 점선은 도색 포함률 99.43%인데도 기존 16프레임 전부 UNKNOWN이었다. 밝은 도색 끝점이 공백 검증용 corner의 상대 응답 기준을 높여 아스팔트 특징점이 배제되는 현상을 확인했다. 흰색과 노란색에서 도로 공백의 증거가 색상 밝기에 따라 달라지는 문제였다.

공백 검증용 특징점에서는 선택 도색 주변 15×15 이웃을 제외한다. 도색 끝점은 별도의 물리 대응 감사에 사용하고, 도로 공백의 특징점으로 세지 않는다. 큰 근거리 이동에서 다른 도로 무늬로 수렴하는 일을 줄이도록 LK 초기 위치를 ego 예측으로 설정했다. forward/backward 0.8px, ego 재투영 2px 조건은 그대로다. 초기 위치가 예측과 같다는 이유로 대응을 승인하지 않는다.

## ego motion 좌표·시각·투영 감사

좌표는 calibrated x 전방·y 우측·z 아래이며 양의 yaw는 우회전이다. `local→world`는 `R(yaw) p+t`, 역변환은 `Rᵀ(p−t)`이다. livePose의 장치 각속도는 `R(rpyCalib)ᵀ`로 calibrated frame에 회전한다. 단위는 rad/s다. 차량 ESP yawRate의 불분명한 단위를 섞지 않았다. 합성 일정 우회전·이동 및 역변환 테스트로 부호를 확인했다. 실사 짧은 쌍은 회전량이 작아 이 자료만으로 모든 회전 조건이 검증된 것은 아니다.

기존 5Hz 선택 프레임 사이 사다리꼴 적분을 모든 carState·livePose 기록 주기의 적분으로 교체했다. 정확한 카메라 EOF를 삽입하고 float 보간 전에 시각 원점을 뺀다. livePose `timestamp`는 측정 시각, logMonoTime은 도착 시각으로 구분했다. 도착 지연 중앙값은 약 22.4~24.7ms다. 카메라에서 끝나는 입력은 EOF로 정확히 대응하지만, 전체 기록 보간은 미래 도착 표본도 활용하는 **오프라인 감사**다. 실시간 causal 구현 검증으로 주장하지 않는다. 카메라 SOF·EOF·integLines도 별도 보존했다. 저장소 OS04C10 readout 값은 11ms이며, 행별 rolling shutter·노출 중심 시각 보정은 검증하지 않았다.

3초 끝 위치의 기존 대비 차이는 클립별 0.057/0.018/0.045/0.020/0.029m다. yaw 차이는 최대 약 0.00156rad다. 이전의 수십~수백 px 잔차를 이 차이만으로 설명할 수 없다.

기존 코드에는 pitch·roll을 버리고, 이전 정적 도색점의 높이를 매번 새 modelV2 도로 z로 교체하는 문제가 있었다. 예를 들어 `38883→38884`에서는 근거리 model 도로 높이가 약 3.5cm 변한다. 이 변화는 실제 카메라 heave의 실측값이 아니다. 새 선택적 `road_pose` 경로는 전체 IMU 회전을 적분하고 이전에 관측한 정적 점의 3D 높이를 보존해 투영한다. 원본 픽셀 좌표만 변환하며 학습 이미지를 warp하지 않는다. 자세 행렬의 회전·행렬식 검증, 자세 표현 전환 시 초기화, 정적 끝점 높이 보존 테스트를 추가했다. 이 수정으로 계측에 빠졌던 자유도는 반영했지만, 실제 지면 깊이·heave 오차까지 해결된 것은 아니다.

### 실제 물리 대응의 근거와 한계

독립 영상 후보 감사에는 ego 예측으로 잔차를 거르지 않는 SIFT 상호 고유 대응과 2차원 corner 대응을 사용했다. 길게 뻗은 한 방향 edge는 고유값 비율로 제외하고, 도로 평면 밖의 방호벽·기둥을 구분하도록 ego 쪽 노면 탐색 영역을 만들었다. SIFT의 엄격한 대응은 여전히 두 물리 부근에 모여 충분한 도로 길이를 검증하지 못했다. 일반 corner 대응에는 반복 홈·그림자·유사 도색의 잘못된 대응과 평면 가정 위반이 남는다.

클립 순서 18379/38875/7039/8042/8355에서 초기화는 0/6/0/4/6→0/2/0/4/7, 경로 선택 불가 프레임은 0/6/0/5/5→0/2/0/5/8이다. `8355`의 경로 부재가 3프레임 늘어나는 회귀 때문에 전체 초기화 감소만으로 채택하지 않는다. 그 클립의 경계 신뢰도 저하와 근거리 경로 지지 부족이 남아 있다. 종류 전환은 모두 UNKNOWN 포함 상태 변화이며 실제 CAN 표시 전환이 아니다.

노란색 원시 출력 30→29는 7039/8355 두 부분 검수의 색상 정확도나 노란색 Recall 하락률로 계산할 수 없다. 전체 프레임별 가시성·색상 정답이 승인되지 않았으므로 노란색 Recall, 흰색 오인율, 전체 분류 Precision/Recall/F1, 실제 False Dashed 비율은 **측정 불가**다. 실제 점선 전환 시작 시점 라벨이 없어 실사 판정 지연도 측정 불가다. 모형 내부 .95/.85는 보정된 신뢰 확률이 아니다.

## 원래 카메라 주기 누적 대조: 실제 흰 점선 누락의 추가 원인

5Hz 수정 후에도 실사 점선이 0/32라서 같은 5개 구간의 **원래 연속 영상 305프레임(각 61개, 약 20Hz)**을 추가로 처리했다. 새 route나 장면을 수집하지 않았다. 모든 프레임에서 encode/model/camera frameId·EOF 정확한 대응을 다시 요구하고, 동일한 원본 픽셀 선택·거리 bin·18m/22m·2px·0.18m 조건을 유지했다. 프레임 수 다수결로 바꾸지 않았다. 공통 80시점의 RGB 해시·modelV2 기하·EOF는 일치하며 적분 pose의 최대 위치 차이는 약 4.3×10⁻⁷m다. 이 실험은 같은 로그의 관측 주기 대조이며 5Hz 처리와 계산량·입력 관측 수가 다르다.

| 흰 점선 클립 | 5Hz 누적 점선 출력 | 20Hz 누적 후 같은 16시점 점선 출력 | 전체 61관측의 점선 출력 | 클립 시작 후 최초 출력 |
|---|---:|---:|---:|---:|
| 18379 | 0/16 | 5/16 | 18/61 | 2.150초 |
| 38875 | 0/16 | 4/16 | 15/61 | 2.003초 |
| 합계 | 0/32 | 9/32 (28.13%) | 33/122 (27.05%) | 실제 전환 지연 정답 없음 |

차량 속도가 약 19~21m/s이면 5Hz 간격 동안 약 4m를 이동한다. 20Hz에서는 약 1m다. 같은 도색·공백을 더 짧은 이동 간격에서 추적하자 반복 공백이 살아났다. **남은 누락에는 관측 간격에 따른 도로 특징 대응 손실도 관여한다.** 픽셀 선택 개선만으로는 충분하지 않았다. 더 많은 관측을 사용한 실험이므로 모델 원시 정확도의 개선율로 주장하지 않는다.

전체 305프레임에서는 점선 33·실선 52·UNKNOWN 220을 출력했다. 기존과 같은 80시점만 보면 점선 9·실선 13·UNKNOWN 58이다. 점선 출력은 두 흰 점선 클립에서만 발생했다. 나머지 183관측의 점선 출력은 0이지만, 모든 프레임의 종류·가시성 정답이 독립 승인된 것은 아니므로 실제 False Dashed 비율이나 Precision/F1은 계속 측정 불가다. 검토된 268개 도색 core 행에서 가짜 공백은 여전히 0이고 다섯 anchor의 도색 포함률·주변 표시 혼입은 5Hz 수정 결과와 같았다.

추적 generation 초기화는 클립별 0/6/0/16/29다. 관측이 네 배 가까이 많고 연속적인 경로 부재에서도 매번 generation이 증가하므로 5Hz 초기화 횟수와 같은 물리 사건 수로 비교하지 않는다. 특히 8042·8355의 경로/가림 문제가 해결된 것은 아니다. 실제 원본 끝점 두 쌍과 영상 corner 후보 검증의 한계도 그대로 적용된다. 이 점선 출력들을 승인 라벨로 변환하지 않았다.

`dense-control/PREVIEW.html`은 20Hz 관측으로 누적한 뒤 **같은 80시점만 5Hz로 보여 주는** 검수본이다. `dense-control/real-results.json`에는 전체 305관측이 있다. 고속에서 관측 추적은 카메라 주기로 유지하고 최종 종류/표시는 5Hz로 갱신하는 구조를 검토할 근거가 생겼다. 다만 이번 구현은 매 관측에서 전체 오프라인 선택기를 실행한 대조다. 경량 실시간 특징 추적 구현이나 Snapdragon CPU 비용은 검증하지 않았으며 현재 daemon 실행 주기는 바꾸지 않았다. 계산 비용과 물리 정렬 검증 전에는 실차 구조로 채택하지 않는다.

## 거리 중복·가림·초기화·저속 22m 조건

거리 bin은 .25m이며 동일 경계의 동일 공간 bin을 프레임 수로 중복 가산하지 않는다. 3초 만료, 공백 확인 전 이동 .5m, 3개 도색 그룹·2개 실측 공백·18m 점선 조건을 유지했다. UNKNOWN·가림은 음성 도색 정답이나 새 공백이 아니다. 상충한 공간 증거는 UNKNOWN이며 이전 증거의 시각을 갱신해 수명을 연장하지 않는다. 차선 변경, 경계 신뢰 상실, 시각 역행/큰 공백, 부적절한 자세 입력, 경계 대응 실패 시 초기화를 유지한다. 기존 .5초 표시 보존 정책과 CAN 표시 값은 변경하지 않았다.

합성 동일 실선·정확한 ego pose·0~3초·5Hz에서:

| 속도 | 첫 실선 출력 | UNKNOWN 비율 |
|---|---:|---:|
| 정차 | 없음 | 100% |
| 1m/s | 없음 | 100% |
| 2m/s | 없음 | 100% |
| 3m/s | 2.8초 | 87.5% |
| 5m/s | 1.6초 | 50% |

22m 조건은 저속에서 지연만 늘리는 것이 아니라 3초 관측 창 안에서 성립하지 않을 수 있다. 이상적인 4.5~20m 전체 15.5m가 보여도 추가 최소 6.5m 이동이 필요하다. 정속 약 2.17m/s 이하는 이상적 관측에서도 3초 창의 22m를 채울 수 없고, 보닛/FOV/그림자 제외가 있으면 더 제한된다. 22m를 낮추지 않았다. 저속에서 점선의 공백이 안 보인다는 이유로 실선으로 대체하지 않는다. 현재 실사 80프레임의 속도는 약 8.3~21m/s여서 이 저속 표를 실차 저속 실측으로 주장하지 않는다.

## 검증·재현·최종 판단

77개 차선 관련 테스트와 수정 코드 Ruff 검사를 통과했다. 3차원 정적 점 보존, yaw 부호·정확한 카메라 시각 삽입, 부적절한 자세, 파란 그림자 흰 도색, 흰/노란 점선의 반복 공간 공백, 정차 중 거리 중복 금지, UNKNOWN/가림·초기화 기존 보호를 확인했다. 합성 입력과 원본 HD 재생 결과는 별개다. Windows PC 오프라인 코드 검증이며 comma Snapdragon 실측, 실시간 NV12 검증, 실차 CAN 검증은 수행하지 않았다.

재현은 저장소 루트에서 다음과 같다. 학습 명령은 없다.

```powershell
powershell -NoProfile -File .analysis/pixel-ribbon-alignment-20261018/REPRODUCE.ps1
```

`REPRODUCE.ps1`은 이번 감사 폴더의 생성 결과만 재생성한다. 최초의 80프레임 manifest와 끝점 검토 파일은 함께 보존해야 한다. 전체 로그 보존 검증은 SHA-256 기준 405/405 일치, 기존 CAN·debug·모델 바이너리 등 민감 파일 97개 차이 0, 이전 Pixel Ribbon 결과 차이 0이다. 활성 ONNX SHA-256은 `ea76f53a26cff8f0182700f39216475bd4b2454d5967dc48d991dd0b451b132f`로 동일하다. `preservation.json`, `validation-plan.json`에 결과·코드 해시가 있다. 별도 사용자의 기존 미커밋 수정은 유지했다.

산출물은 `PREVIEW.html`(80프레임 원본/mask), `white-layers-*.png`, `white-trace-audit.json`, `endpoint-results.json`, `endpoint-prediction-*.png`, `pair-correspondence/`, `corner-correspondence/`, `odometry.json`, `telemetry-attitude/`, `comparison.json`, `slow-solid22m.json`, `final-tests.txt`이다.
