# CCNC HDA1 전방 옆 차량의 가상 후방 인계 — 구현·오프라인 검증

2026-10-18, `ccnc-hda1`. **사용자 요청에 따라 기존 `CcncRadarVehicles` ON에 가상 후방 인계를 연결했다. 옵션 자체의 기본값은 OFF(0)를 유지한다. 기기 설치와 실차 실측은 수행하지 않았다.**

새 LF/RF가 나타났다는 이유로 기존 가상 LR/RR을 지우지 않는다. 기존 후방 차량을 퇴장시키면서 별도의 전방 후보를 검증하고, 새 차량의 유효한 원점 통과가 성립한 순간에만 더 가까운 새 차량으로 후방 슬롯을 교체한다. 이전 차량의 거리를 0으로 되감는 보간은 하지 않는다. BSD가 활성화되면 두 기억을 폐기하고 기존 BSD 정책이 우선한다.

## 기존 동작과 실측 근거

[계기판 영상 실측](ccnc_cluster_video_20261018.md)에 따르면 LF/LR의 거리 0은 같은 표시 원점이다. RF/RR의 대칭 관계는 사용자 확인이며 영상의 직접 시험 대상은 LF/LR이다. 이 사실은 표시 원점의 대응을 뒷받침하지만, 후방 차량의 실제 위치·속도를 계측한 근거는 아니다.

기존 전방 차량 표시는 거리 0.8 배율과 기존 selector/map·위치 보정을 사용한다. 기존 HDA1 후방 표시는 BSD 활성 시 필터 목표 8, 해제 시 목표 16으로 이동하고 필터가 15 이상이면 사라지는 구조다. 실제 후방 레이더 객체를 생성하는 기능은 없었다.

공유 표시 정책을 `hyundaicanfd_ccnc_rear.py`에 추가하고, selector와 radar map의 **기존 BSD 계산 다음**에 같은 정책을 호출했다. CAN 패킹, 기존 경고 비트, 주기·카운터 처리는 그대로 사용한다. 조향·가감속·레이더 지도 선택·관측·객체 생성은 변경하지 않았다.

## 인계 조건과 예외

- 기존 LF/RF에 실제로 선택·표시된 `frontRadar`의 measured·trackState=2 관측만 후보가 된다. 같은 source와 객체 생성 epoch를 함께 기억한다.
- 최소 4회 신선한 관측, 그중 motionState=2가 최소 3회, 관측 기간 0.3초 이상, 전후 이동 0.25m 이상을 요구한다. 상대속도는 -0.3m/s 이하이며, 초기 퇴장속도가 상한을 넘으면 인계를 생략한다. map 경로는 기존 차량 판정과 구조물·횡단 객체 배제도 요구한다.
- 한 번 읽은 radar 메시지를 반복 읽어도 관측 횟수는 늘지 않는다. 원본 메시지의 신선도, 동일 객체의 위치·횡방향·속도 innovation을 검사한다. 객체 교체는 이전 후보의 확인 이력을 상속하지 않는다.
- 측정 중인 전방 상대 위치·속도 표시는 기존 그대로다. 전방 선택이 끊기면 마지막 원시 x가 6m 이하이고 마지막 관측 이후 1초 안에 원점을 통과할 수 있는 확인된 후보만 짧게 연장한다. 선택기에서 배제됐지만 여전히 x>=1m의 유효 관측이 있는 객체는 연장하지 않는다.
- 연장은 마지막 **실제 표시 거리**에 마지막 유효 상대속도×0.8을 적분한다. 기존 표시 예측으로 화면 위치를 앵커링해도 실제 관측 시각·속도·차량 확인 횟수는 갱신하지 않는다. 원점 통과는 이 제한된 연장의 예측이며 후방 실측이 아니다.
- 후방 인계 시 전방 표시를 끄고 후방 거리와 필터를 정확히 0으로 초기화한다. 같은 identity epoch의 재인계를 억제한다. 새로 측정된 실제 전방 이동은 가상 기억보다 우선하지만, 가상 차량을 전방 객체로 되돌리지 않는다.
- 신호/모델 차선 변경, 다른 슬롯으로의 동일 객체 이동, 차선 신뢰도 상실, CAN 무효, 후진, 0.2초 초과 갱신 공백·시간 역행, selector/map 문맥 변경 시 관련 기억을 버린다.
- 전방 후보와 후방 가상 차량은 각각 좌우 한 개씩 별도 보관한다. 기존 후방이 있어도 새 전방 후보를 검증한다. 새 인계 시 `rear_replaced`로 이전 후방을 종료하고 새 차량을 0에서 시작한다. 대기열이나 이전 후방 복원은 없다.

차량 확인은 레이더 필드와 기존 선택기의 증거에 의존한다. 실제 차량과 객체 ID의 동일성을 완전히 증명하는 영상 객체 추적기를 추가한 것은 아니다. 따라서 반사체 오인 가능성이 물리적으로 제거됐다고 주장하지 않는다.

## 퇴장 파라미터와 BSD 우선순위

| 항목 | 오프라인 시제품 값 | 의미 |
|---|---:|---|
| 초기 후방 속도 | `-마지막 vRel × 0.8` | 자차 속도만으로 상대 운동을 대체하지 않음 |
| 가속 시작 | 마지막 유효 관측 후 0.8초, 단 인계 이전으로 소급하지 않음 | 관측이 오래 끊기면 퇴장 가속 |
| 추가 가속도 | 1.2 표시거리/s² | 시간 간격 안의 가속 시작·상한 도달까지 해석적으로 적분 |
| 속도 상한 | 8 표시거리/s | 처음부터 이 속도를 넘는 후보는 인계하지 않음 |
| 거리 종료 | 16 | 도달한 프레임에 삭제, 잔여 회색 ghost 방지 |
| 최대 가상 추적 | 인계 후 6초 | 추가 상한, 이후 복원 없음 |

단위는 기존 0.8 투영을 적용한 **표시 좌표**다. 실제 후방 차량이 이 가속도로 이동한다는 뜻이 아니다.

기존 테이프에서 지연 0.5/0.8초 × 가속도 0.8/1.2/1.6 × 상한 6/8 × 최대시간 4/6/8초, 36조합을 비교했다. 상한 6은 마지막 상대속도가 큰 3건을 추가로 거부해 인계 8건, 상한 8은 11건이었다. 지연 0.8·상한 8·최대시간 6 조건에서 가속도 0.8/1.2/1.6의 평균 유지시간은 2.764/2.625/2.525초, 최대는 3.45/3.15/2.95초였다. 중간 가속도 1.2를 사용했다. 최대시간 4/6/8은 실제 11건에서 모두 timeout이 없어 우열을 정할 수 없었다. 가장 느린 허용 속도의 합성 사례가 6초 전에 거리 16에 도달함도 확인했다.

**이 값들은 로그에서 연속성과 유한 퇴장을 확인한 시제품 값이다.** 실제 후방 정답이나 계기판 주관 평가로 최적화한 값은 아니므로 실차 확정값으로 채택하지 않는다. [전체 비교](../.analysis/ccnc-rear-handover-20261018/final2/parameter-sweep.json)

BSD가 이미 켜졌으면 후보 확인과 가상 인계를 시작하지 않는다. 가상 후방 표시 중 BSD가 켜지면 전방 대기 후보와 후방 가상 기억을 즉시 폐기하고, 실제로 그리던 거리에서 기존 필터를 통해 8로 수렴한다. BSD 해제 시 기존 16 퇴장 정책을 사용하고 이전 가상 차량을 복원하지 않는다.

BSD 활성 상태의 필터 법칙·DETECT·횡위치는 보존된다. 가상 퇴장으로 필터 이력이 달라지므로 모든 BSD 거리의 비트 동일성은 주장하지 않는다. 재생에서 selector의 BSD 거리 부동소수 차이 865 side-send, 최대 0.041407 표시거리, 0.1 단위 반올림 코드 차이 34 side-send가 있었고, map은 모두 0이었다. BSD DETECT/횡위치 차이는 양 경로 모두 0이다. 반올림 코드 비교는 오프라인 수치 비교이며 실차 수신 CAN 실측은 아니다.

동일 identity의 LF/LR 또는 RF/RR 중복은 가상 후방 577 side-frame의 검사에서 0이었다. 서로 다른 전방 차량+후방 차량, 또는 실제 전방+BSD가 동시에 보이는 정상 상태는 중복 차량으로 세지 않았다. BSD 활성 필터 법칙은 두 경로 합계 60,264 side-send에서 확인했다. 실제 가상 후방 중 BSD가 켜지는 사례는 이번 11건에 없어 해당 전환은 합성 시험으로 검증했다.

영상에서 옆 차량이 존재하는 문맥은 확인했지만 **잘못된 인계 0건, 실제 차량 놓침 0건, 후방 위치 정확도 X%는 판정할 수 없다.** 레이더 ID-영상 차량 대응의 미확정과 실제 후방 정답 부재가 남아 있다. 마지막 상대속도 이후 옆 차량이 가속·감속하거나 차선을 바꿔도 관측 없이 알아낼 수 없고, 길이가 긴 차량의 반사점 원점은 차체 끝과 다르다. 추가 퇴장 가속은 관측을 잃은 표시를 제거하기 위한 정책이다.

- 회귀 검사: 1,260 통과, 3 skip. 이후 최소 허용 상대속도 사례를 추가한 최종 집중 검사: 26 통과(기존 25개를 포함하므로 합산하지 않음).

- selector/map 두 경로에서 실제 CANPacker와 `create_ccnc_messages`를 사용한 합성 시험도 수행했다. 주소·버스·메시지 순서가 같고 0x162 이외 메시지 바이트가 동일하다. 0x162는 옆/후방 표시 필드와 checksum만 차이를 허용하고 FF·경고·카운터 등 나머지 신호 동일성을 검사했다. CAN 소켓이나 장치로 송신하지 않았다.
- 신규 모듈·신규 테스트 Ruff 검사 통과. 원본 보존 스냅샷 182개 중 의도한 기존 표시 코드 3개 외 179개 해시가 일치했다. 별도 CCNC 디버그, 주행 제어, lane-type/ONNX 등 스냅샷 대상은 유지됐다. 원본 로그를 수정하는 경로는 없다. [보존 결과](../.analysis/ccnc-rear-handover-20261018/preservation.json)

수정 파일은 `hyundaicanfd.py`, `hyundaicanfd_ccnc_extension.py`, `hyundaicanfd_ccnc_radar_map.py`의 작은 호출부와 신규 `hyundaicanfd_ccnc_rear.py`, 집중 테스트 두 파일이다. 신규 의존성은 없다. 대량 로그는 실제 주행 당시 CAN 출력 재현이나 폐루프 주행 제어 검증이 아니라, 기록된 입력으로 현 표시 코드를 오프라인 재생한 것이다.

**활성화 연결:** `create_ccnc_messages(..., rear_handover=True)`를 기본으로 바꾸어 실제 호출자에서 `CcncRadarVehicles`를 켜면 기존 selector와 radar map 양쪽에서 가상 후방 인계도 작동한다. `configure`의 기존 `rear_handover and radar_vehicles` 조건과 HDA2 차단을 그대로 사용하며, 별도의 Params/UI 옵션은 없다. 옵션을 끄면 가상 기억을 폐기하고, 다시 켜도 과거 차량을 복원하지 않는다. 기존 설정 확인 주기(100프레임)를 그대로 따르므로 실시간 토글은 다음 확인 때 반영된다. 시험에서는 인계 알고리즘의 기존 출력과 비교할 수 있도록 명시적 `rear_handover=False`를 계속 허용한다.

사용자의 실차 실행 경로 연결 요청에 따른 후속 변경이다. 앞선 커밋 `489e1654`의 적용 보류 상태를 해제하지만, 오프라인 검증을 실차 검증으로 바꾸어 해석하지 않는다. 현재 장치 연결이 없어 실제 차량에 설치하거나 계기판 동작을 측정한 것은 아니다.
