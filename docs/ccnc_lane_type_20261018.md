# CCNC 차선 종류·색상 분류 시범 구현 — 2026-10-18

`Qualified4/openpilot`, `ccnc-hda1`에서 별도 PP-LCNet-0.25x 분류기와
OpenCV 비교기를 구현했다. **두 방식 모두 실차 적용을 보류한다.** 학습된
ONNX는 실제로 생성했지만 표본이 작고 미확정 비율이 높아 정확도 승인 상태가
아니다. OpenCV는 PC에서 더 가볍지만 이 표본의 정확도가 충분하지 않아 우선
추천하지 않는다. `CcncLaneTypeDetection`은 기본 OFF이며 실차 CAN 출력은
연결하지 않았다. 커밋·푸시·장치 설치는 수행하지 않았다.

## 구현과 적용 범위

- `openpilot/selfdrive/carrot/lane_type`: ROI, 독립 데몬, 두 분류기,
  관측 보호·만료 및 송신 없는 CCNC 미리보기.
- `tools/lane_type`: 동기화 추출·검수 큐, PC 미세조정·ONNX 변환,
  동일 데이터 평가·PC ON/OFF 벤치마크와 테스트.
- `assets/lane_type.onnx`: FP32, **245,308 parameters / 1,000,121 bytes**.
  모델 SHA-256은 동봉 `manifest.json`으로 고정한다.
- 옵션 ON은 독립 `ccnc_lane_type` 프로세스를 실행한다. OFF에서는 프로세스를
  시작하지 않으며 수동 실행도 OpenCV import·모델 로드 전에 종료한다.
- 기존 카메라의 공유 NV12를 작은 ROI로 직접 샘플링한다. 전체 RGB 프레임
  변환·복사는 하지 않는다. 좌우 유효 ROI를 최대 2개 배치로 처리하며 목표는
  5Hz다. 관측 부족·차선 변경 때는 추론 자체를 생략한다.
- 기존 조향·가감속·차선 변경 제어, Xiaoge, Hyundai CAN 생성 파일은 수정하지
  않았다. `customReservedRawData2`에 결과·엔진·원본 timestamp·신뢰도·관측
  길이·가림·추론/처리/스레드 CPU 시간을 기록한다. 추론하지 않은 cycle의
  `inferenceMs`는 null이며 0ms 실측으로 취급하지 않는다.

PP-LCNet은 [공식 PaddleClas 구현](https://github.com/PaddlePaddle/PaddleClas/blob/release/2.6/ppcls/arch/backbone/legendary_models/pp_lcnet.py)의
0.25x 구조를 PyTorch로 이식하고 공식 ImageNet 사전학습 tensor **144개**를
불러왔다. 새 종류·색상 이진 head를 각각 미세조정했다. 공식 체크포인트
SHA-256은 `916a60d5db8669709550bd799e0ca95ab55c1fbd3154cf762dc48112d0f47afe`다.
Apache-2.0 라이선스 사본을 포함했다. PyTorch·ONNX·ONNX Runtime·PyAV·psutil은
PC 도구용이며 comma에는 추가하지 않는다. 장치 추론은 기존 OpenCV DNN CPU
backend와 1개 OpenCV thread를 사용한다.

OpenCV 비교기는 같은 RGB ROI에 HSV 색상 마스크, 행별 도로 대비,
차선 중심 영역의 거리 방향 연속성·공백 길이를 적용한다. 객체 검출은 없다.
OpenCV 점수는 휴리스틱 증거량이고 PP-LCNet softmax도 보정된 정확도 확률이
아니다. 두 방식의 confidence를 동일하게 보정됐다고 해석하지 않는다.

## 데이터와 라벨 검수

로컬 쏘나타 디 엣지 20개 segment에서 5/15/25/35/45/55초를 샘플링했다.
인코딩 frame index와 camera EOF, modelV2 EOF 및 보정된 카메라 행렬을 연결했다.
추출한 200개 좌우 ROI의 모델/카메라 EOF 차이는 모두 0이었다. 유효하지 않은
전체 길이·차선 확률·투영 영역 등으로 제외한 ROI는 기본 데이터에 들어가지
않았으므로, 200개가 모든 카메라 관측의 분모는 아니다.

ROI는 modelV2 안쪽 좌우 경계를 따라 **6~46m, 폭 0.9m → 64×192 RGB**로
펼친다. 작은 점 패치 대신 40m의 공백·연속성을 보존한다. 일부 영상은 원본
fcamera이고 일부는 압축 qcamera다. qcamera의 해상도·흐림과 인코딩 RGB가
실시간 NV12의 색상/노이즈와 동일하다고 검증하지 않았다.

자동 마스크 결과는 `suggestion`에만 저장했다. ROI와 전체 프레임을 직접
확인한 **단일 Codex 시각 검수 61개**만 참조 라벨로 사용했고, 가림·혼합
표시·경계 대응이 불분명한 것은 정답으로 승격하지 않았다. 검수자·방법·메모와
이미지 해시를 남겼다. **독립적인 사람 검수는 없으므로 공인된 정답 집합이나
제품 승인 수준의 라벨 품질을 주장하지 않는다.**

전체 route를 한 split에만 배정했다. 같은 프레임의 좌우나 인접 segment도
분리되지 않아 segment 분할보다 강하게 누수를 제한한다. 이미지 hash 중복도
검사한다. 검수·충분한 관측·차선 변경 제외 조건 뒤의 모델 개발 표본은 다음과
같다. test는 학습·체크포인트 선택에 사용하지 않았다.

| 분할 | route 수 | ROI 수 | 점선 / 실선 | 흰색 / 노란색 |
|---|---:|---:|---:|---:|
| 학습 | 3 | 30 | 12 / 18 | 25 / 5 |
| 검증 | 3 | 8 | 6 / 2 | 6 / 2 |
| 테스트: 충분한 관측·비차선변경 | 3 | 21 | 13 / 8 | 14 / 7 |

학습은 CPU에서 30 epoch, 작은 batch의 BN running statistics는 사전학습 값으로
고정했다. 검증 loss가 가장 낮은 epoch 2를 선택했다. PyTorch → ONNX Runtime
출력 최대 절대 오차는 **7.60×10⁻⁷**였고 OpenCV DNN의 실제 1/2 ROI 추론도
테스트했다. 이는 변환·실행 검증이며 차선 정확도 검증과 다르다.

5개뿐인 불균형, 흐린 ROI와 경계/색상 domain 차이가 남는다.

OpenCV는 충분한 테스트 ROI 21개 모두 `no_paint_evidence`였다. 고정 마스크·대비·
유효 픽셀 조건이 이 전송 영상 domain에 충분히 맞지 않았다는 결과다. 낮은
해상도·흐림·그림자·투영 오차가 원인 후보지만 기여분을 분리 측정하지 않았다.
테스트 결과에 맞춰 임계값을 다시 튜닝하지 않았으며 재개선에는 별도의 미사용
테스트 route가 필요하다. 오분류·미확정별 원본 ROI 대응은 로컬 JSON에 남겼다.

곡선은 modelV2의 6~46m 횡변위가 1m를 넘는 기하 기준이며 물리적 곡률의 별도
정답 검수는 아니다. 차선 변경은 모델 상태·방향지시등, 저속은 0.1~2m/s,
정차는 0.1m/s 미만이다. 검수된 야간 표본이 없으므로 야간 수치를 만들지 않았다.

두 방식 모두 현재 보수적인 신규 확정 조건은 **사용 가능 길이 ≥32m,
기하 가림 ≤15%**다. 길이는 모델 경계·영상 범위와 기존 leadsV3의 보수적
차량 실루엣을 이용한 usable length이며, 실세계 픽셀 가림의 정답 측정은
아니다. 인지되지 않은 차량·구조물의 가림을 모두 보장하지 못한다.

조건이 부족하면 이전에 threshold를 통과한 종류·색상을 각각 원래 camera
timestamp부터 최대 0.5초 유지하고 만료한다. 반복 정차 프레임이 이를 갱신하거나
관측 거리를 늘리지 않는다. 차선 변경·경계 추적 상실·경계 위치 불연속·오래된
입력에서는 초기화한다. 가림만으로 실선을 새로 확정하지 않는다.

차량 이동으로 여러 프레임의 ROI를 이어 붙이는 방법은 검토했으나 채택하지
않았다. modelV2 lane index는 물리적 차선 ID가 아니므로 잘못된 차선으로 이전
칠 패턴이 전이될 수 있다. 물리적 동일 경계와 odometry 정렬을 검증하기 전에는
공간 관측 길이를 누적하지 않고 현재 관측과 유한한 결과 유지에 한정한다.

`3ed/32`, `3e7/18`에서 별도로 5Hz 연속 ROI 126개를 추출했다. 일부 조건은
중복된다. **두 방식의 결과는 동일**했다.

테스트로 별도 확인했다.

## 성능: PC 실측과 comma 미측정의 구분

Windows 11 / AMD64 Family 25 Model 97 PC, OpenCV 4.13.0, 각 engine/OFF마다
새 프로세스에서 순차 실행했다. 10회 warmup 뒤 8초·40호출, 좌우 ROI 2개/호출,
5Hz 목표다. 전처리 정규화와 분류를 포함하며 공통 카메라 수신·ROI 투영/추출은
제외한다. RSS는 추론 후 표본의 최대 RSS이지 순간 최고치의 연속 측정이 아니다.
짧은 CPU counter 표본이며 OFF의 0.00%는 0 overhead를 보장하지 않는다.

| PC 측정 | OFF | PP-LCNet ON | OpenCV ON |
|---|---:|---:|---:|
| CPU, 1코어=100% | 0.00% | 1.95% | 0.59% |
| 샘플 최대 RSS | 41.46MiB | 51.80MiB | 46.67MiB |
| 추론 평균 / p95 / p99 | 해당 없음 | 2.72 / 3.55 / 3.92ms | 0.48 / 0.63 / 0.82ms |
| 관측 호출 주기 | 해당 없음 | 4.994Hz | 4.994Hz |

이 PC에서 OpenCV의 평균 분류 시간은 PP-LCNet 대비 약 **82.4% 짧았다**.
그러나 이 데이터의 정확도가 충분하지 않으므로 속도만으로 우선 추천하지
않는다. 모델 로드와 공유 카메라의 전체 비용, 지속 주행·열 제한 상황은 이
벤치마크에 포함되지 않았다.

요청한 기존 Xiaoge 비교 기준은 **comma 기록 참고값: 평균 738ms,
CPU 약 160%(한 코어 기준), RSS 약 216MiB**로 보존한다. PC와 comma, 모델 및
입력이 달라 이를 분모로 성능 향상률을 계산하지 않는다.

현재 comma가 연결돼 있지 않아 동일 입력 ON/OFF 장치 재생은 수행하지 못했다.
새 기능의 comma CPU·RSS·추론 평균/p95/p99·실제 갱신 주기·modeld/controlsd
주기/지연·프레임 누락은 **모두 측정 불가**다. 기존 OFF 주행 로그에 새 기능의
ON 성능이 있다고 가정하거나 PC 결과를 실차 결과로 대체하지 않았다.

## CAN 검증 경로와 판정

`result.preview_values`는 기존 표시 값을 복사해, 옵션 ON + `CcncModelLanes`
일반/정밀 + 신선한 side 결과일 때만 `LANELINE_LEFT/RIGHT`에 8/10 후보를
반영한다. 원본 dict는 수정하지 않는다. 종류만 후보이며 흰색/노란색의 Sonata
CAN encoding을 임의로 만들지 않았다. confidence·미확정·만료 조건이 실패한
side는 기존 값을 그대로 반환한다. 이 함수는 CAN 송신기에서 호출하지 않는다.

따라서 실제 계기판 표시 연동은 **송신 없는 미리보기까지**이며, 실차 출력은
항상 기존 경로다. `accuracyValidated`, `deviceValidated`, `canTransmitEnabled`는
모델 manifest에서 모두 false다. 둘 다 기본 OFF와 CAN 미적용을 유지한다.

확정률을 높이려 threshold를 바로 낮추는 것은 원시 후보의 잘못된 실선·색상을
노출할 수 있다. 다음 단계는 독립 사람 라벨 검수, 더 많은 route·야간·고해상도
자료와 marking 전환 정답, confidence 검증, 실제 comma의 같은 입력 ON/OFF
재생, 격리된 계기판 bench의 8/10·색상 검증이다. 현재 결과만으로 실차 적용을
승인하지 않는다.

검증: 분류/관측 보호/기본 OFF/모델 hash·실행/비송신 미리보기 및 기존 CCNC·Wiki
관련 **195 tests pass**, Ruff와 한·영 사용자 문서 검사 통과. Windows에서는
기존 고정 OpenCV와 ASCII full-capnp staging, 기존 Params lookup double을
사용했다. Linux native build나 실제 카메라/차량 실행을 검증한 것은 아니다.
